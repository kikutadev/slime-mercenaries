# Camp & Fusion Blender Asset Production Plan

Status: Ready
Date: 2026-09-17
Owner boundary: Environment / camp / fusion presentation only

## 1. Purpose

Replace the current CSS-symbol mock environment with production-ready 3D assets generated by Blender Python.

This initiative is intentionally separate from the existing slime model / motion gallery production plan.

It does **not** own:

- slime body / job-model production
- weapon collection UI or weapon models
- Forge environment
- Dispatch map
- balance / progression logic
- authoritative Domain / Kit integration

It owns only the assets and runtime presentation required to make **Camp** and **Fusion** look like a finished game.

The first target is one production-quality vertical slice:

> Camp where slimes visibly live and can be selected → training / nursery / formation / fusion altar are physical places → Fusion zooms into the same altar and plays the existing two-slime merge / upgraded-attack sequence in-world.

## 2. Why this is a separate initiative

The current parallel slime-production work edits character-generation and gallery paths. This plan avoids those paths.

New source ownership:

```text
tools/blender/environment/
  common.py
  generate.py
  camp.py
  fusion_altar.py
  training_dummy.py
  nursery_vat.py

public/assets/environment/
  camp-diorama.glb
  fusion-altar.glb
  training-dummy.glb
  nursery-vat.glb
```

Optional QA evidence:

```text
.acceptance/environment/
  camp-default.png
  camp-selected.png
  fusion-ready.png
  fusion-impact.png
  fusion-result.png
```

Do not modify `tools/blender/generate_slime.py` for this initiative.

## 3. Visual direction

Follow `docs/specs/art-direction.md`:

- bright fantasy diorama
- toy-like and slightly rounded
- matte / soft materials
- readable silhouettes on a phone
- no realism chase
- no medieval parchment / ornate frame aesthetic
- no CSS placeholder geometry in the final scene

The world should visually sit in the same family as the existing soft glossy slime models, while remaining less saturated so the slimes stay dominant.

### Material language

Use glTF-friendly Principled materials only.

Primary palette:

- grass: spring green, moderately desaturated
- dirt: warm cream / sandy beige
- wood: medium warm brown
- stone: pale warm gray with green undertone
- cloth: muted clover green / cream
- fusion emissive: pale mint + warm gold
- nursery fluid: aqua / cyan

Avoid texture-map dependency in v1. Form, color, bevels, material roughness and emissive accents should carry the art.

## 4. Asset set — v1

Only assets needed for Camp + Fusion are in scope.

### A. `camp-diorama.glb` — highest priority

One compact playable diorama base containing the non-interactive environment plus fixed prop silhouettes.

Contents:

- rounded grass island / camp ground
- cream dirt path connecting key stations
- low grass / clover clusters
- a few rounded rocks
- one small tent / awning
- one campfire ring or lantern cluster for ambient life
- formation banner / flag
- low wooden fencing or logs used sparingly
- fixed decorative props only

Do **not** include a weapon rack in v1.

Interactive stations are attached at named anchors and may load as separate GLBs.

#### Required node contract

```text
CampRoot
├─ Ground
├─ DirtPath
├─ Tent
├─ FormationFlag
├─ AmbientProps
├─ Anchor_SlimeHome
├─ Anchor_SlimeIdleA
├─ Anchor_SlimeIdleB
├─ Anchor_Training
├─ Anchor_Fusion
├─ Anchor_Nursery
├─ Anchor_Formation
├─ Anchor_CameraFocus
└─ Anchor_CameraTarget
```

Anchors are empty objects exported into GLB.

### B. `fusion-altar.glb` — highest priority

This is the visual centerpiece.

It appears twice:

1. as a real physical object inside Camp
2. as the same asset in the Fusion close-up scene

Contents:

- low circular stone altar
- left and right slime pads
- central merge / result pad
- outer and inner rune rings
- three small material sockets around the perimeter
- 3–4 short stone posts to frame the silhouette
- subtle inset gold / mint accents
- no huge fantasy gate
- no weapon display

The altar should look usable while idle and special when emissive materials are animated at runtime.

#### Required node contract

```text
FusionAltarRoot
├─ AltarBase
├─ RuneOuter
├─ RuneInner
├─ RuneCore
├─ Pad_Left
├─ Pad_Right
├─ Pad_Result
├─ Socket_Core
├─ Socket_CatalystA
├─ Socket_CatalystB
├─ Pillars
├─ Anchor_LeftSlime
├─ Anchor_RightSlime
├─ Anchor_ResultSlime
├─ Anchor_TrainingDummy
├─ Anchor_CameraFocus
└─ Anchor_CameraTarget
```

Runtime must be able to independently adjust emissive intensity for:

- `RuneOuter`
- `RuneInner`
- `RuneCore`

Do not bake the fusion flash into the model. Flash, particles and hit-stop remain runtime presentation.

### C. `training-dummy.glb` — high priority

Shared by Camp training and post-Fusion attack preview.

Design:

- soft wooden post
- round straw / padded body
- simple crossbar silhouette
- visibly toy-like, not realistic torture-device imagery
- broad enough to read at 50–80 CSS px
- damage reaction handled by runtime transform, not skeletal animation

#### Required node contract

```text
TrainingDummyRoot
├─ Base
├─ Post
├─ TargetBody
├─ TargetMark
└─ Anchor_Impact
```

The root origin must sit on the floor directly under the center of the target.

### D. `nursery-vat.glb` — high priority

Replaces the current UI-circle / `●` placeholder language for Plain Slime creation.

Design:

- squat round stone / ceramic basin
- aqua fluid surface
- two or three small glass / ceramic material bowls around it
- soft clover motif
- central spawn position for Plain Slime reveal
- cute crafting station, not laboratory machinery

#### Required node contract

```text
NurseryVatRoot
├─ Basin
├─ Fluid
├─ Bowl_Left
├─ Bowl_Right
├─ CloverMark
├─ Anchor_Spawn
├─ Anchor_CameraFocus
└─ Anchor_CameraTarget
```

`Fluid` should be a separate mesh/material so runtime can pulse / change opacity without touching the basin.

## 5. Intentionally excluded from v1

The following are not needed now and should not consume production time:

- weapon rack
- individual weapon pickups
- Forge machine
- weapon chest / weapon showcase pedestal
- Dispatch props / world map models
- detailed buildings
- NPCs
- texture atlases
- baked lighting
- day/night variants
- complex vegetation simulation

The existing Greatsword carried by Greatsword Slime remains part of that slime asset; this plan does not author new weapon content.

## 6. Blender Python architecture

Use a clean environment generator, not additions to the slime generator.

```text
tools/blender/environment/
├─ common.py
├─ generate.py
├─ camp.py
├─ fusion_altar.py
├─ training_dummy.py
└─ nursery_vat.py
```

### `common.py`

Own reusable helpers:

- `clear_scene()`
- `make_material()`
- `make_emissive_material()`
- `create_box()`
- `create_cylinder()`
- `create_rounded_disc()`
- `create_curve_strip()`
- `create_rock()`
- `create_anchor()`
- `apply_bevel()`
- `apply_transforms()`
- `export_glb()`
- material reuse / caching

### `generate.py`

CLI:

```bash
blender -b --python tools/blender/environment/generate.py -- \
  --asset camp \
  --output public/assets/environment/camp-diorama.glb
```

Supported values:

```text
camp
fusion
training-dummy
nursery
all
```

`--asset all` emits all v1 files into `public/assets/environment/`.

### Determinism

Procedural decorative placement may use randomness only with one fixed seed checked into source. Re-running the generator must produce the same scene layout.

## 7. Scale and coordinate contract

Use Blender meters as game-world logical units.

Reference:

- normal slime body width: roughly 1.8–2.2 units
- training dummy height: ~1.6 units
- fusion altar overall diameter: ~4.6–5.2 units
- each slime fusion pad center offset: ~1.1–1.3 units from center
- Camp usable island: ~9.5 × 7.0 units

Blender source is Z-up; export GLB with `export_yup=True`, matching the existing slime pipeline.

All asset roots:

- origin at floor center unless specifically documented otherwise
- scale `(1, 1, 1)` after export
- no hidden camera/light objects in production GLB
- no unapplied object transforms on render meshes

## 8. Mobile-performance budget

Target the actual iPhone portrait game, not Blender beauty renders.

### Triangle budgets

- `camp-diorama.glb`: <= 18k triangles
- `fusion-altar.glb`: <= 8k triangles
- `training-dummy.glb`: <= 2k triangles
- `nursery-vat.glb`: <= 4k triangles

Total environment visible in Camp should normally stay under ~30k environment triangles before slime models.

### Material / draw-call intent

- camp materials: <= 8
- fusion altar materials: <= 5
- dummy: <= 3
- nursery: <= 4
- reuse shared material values aggressively
- avoid alpha blending except nursery fluid if necessary

No 4K or 2K textures in v1 because v1 should require no image textures.

## 9. Camp composition

The asset should be authored for the real portrait camera, not front orthographic presentation.

Recommended spatial composition:

```text
           [ Tent / idle area ]

 [ Training ]      [ Fusion altar ]

          [ selected slime ]

 [ Nursery ]       [ Formation flag ]

             camera
```

This is not a literal menu grid. Objects must be placed with irregular natural spacing and depth so it reads as a campsite.

The selected slime remains the visual focal point.

Interactive stations should remain visually identifiable with **no text labels**.

## 10. Fusion close-up composition

Reuse `fusion-altar.glb`.

Camera framing must clearly fit:

- left source slime
- right source slime
- central rune
- result slime
- dummy used for upgraded-attack preview

Sequence support:

1. idle altar, low rune glow
2. material sockets activate
3. two slimes compress / move toward center
4. short flash / hit-stop
5. result slime appears on `Anchor_ResultSlime`
6. result attacks dummy at `Anchor_TrainingDummy`
7. camera holds long enough to read the new form

The Blender asset does not own character animation. It owns stage geometry and anchors only.

## 11. Runtime integration plan

After GLB acceptance, replace CSS mock geometry in Camp.

### Camp

Remove / stop rendering:

- `.camp-world__sky` as fake game object where 3D backdrop replaces it
- `.camp-world__hills*`
- `.camp-world__ground`
- Unicode prop silhouettes `▲ / ＋ / ✦ / ⚑`

Add a Three.js Camp scene that loads:

- `camp-diorama.glb`
- `fusion-altar.glb`
- `training-dummy.glb`
- `nursery-vat.glb`
- currently selected slime GLB

HTML controls remain overlays only where necessary.

Station hit areas should be projected from named 3D anchors or use simple Three.js raycast hit meshes.

### Fusion

Replace the generic round presentation platform with the actual `fusion-altar.glb`.

Keep current authoritative flow:

`Domain fuse command -> immutable presentation run -> animation only`

Do not move progression state into Three.js.

## 12. Interaction / animation using static Blender assets

Do not over-author baked animation in Blender.

Most environment motion is simpler and easier to tune in runtime:

- Fusion rune emissive pulse
- altar material socket glow
- nursery fluid pulse
- flag sway (small procedural rotation)
- campfire / lantern flicker
- training dummy recoil / spring return
- camera push-in / orbit shift

Blender provides named rigid parts and stable pivots.

## 14. Acceptance gate — Camp

Camp is accepted only when:

1. A screenshot with text hidden still obviously looks like a game campsite.
2. No Unicode placeholder represents a world object.
3. The selected slime remains the strongest focal point.
4. Training / Fusion / Nursery / Formation stations are visually distinguishable without labels.
5. At least 60% of the useful viewport is world / character presentation rather than cards.
6. Props do not visibly clip the slime at default idle anchors.
7. Station selection causes a meaningful camera/world response.
8. Scene remains readable at 390×844.
9. No new console errors.
10. Camp frame rate does not materially regress relative to current Battle scene on the same device/browser.

## 15. Acceptance gate — Fusion

Fusion is accepted only when:

1. The physical altar is recognizable before any UI copy is read.
2. Two source slimes visibly stand on separate physical pads.
3. Ingredient sockets read as physical altar components, not floating cards.
4. Merge center is spatially obvious.
5. Greatsword result does not clip the altar or pillars.
6. Horizontal sweep has clear space and hits the physical dummy.
7. Dummy recoil makes impact readable.
8. Rune glow escalates before impact and settles after result.
9. Closing / reloading during presentation cannot duplicate or undo Domain progression.
10. Screenshot sequence `ready -> converge -> impact -> reveal -> attack -> complete` is visually coherent.

## 16. Parallel-safety rules

This initiative can run at the same time as slime-gallery production because it owns separate files.

Do not edit:

- `tools/blender/generate_slime.py`
- `src/gallery/slimes/*`
- slime branch content briefs
- existing slime GLBs

Environment work may edit later, during integration only:

- `src/screens/SlimesScreen.tsx`
- `src/components/fusion/*`
- new `src/components/camp/*`
- new `src/game/environment/*`
- `src/style.css` only for overlay cleanup

Before that integration phase, keep production work confined to the new environment paths.

## 17. Definition of done

This initiative is complete when:

- all four v1 GLBs are reproducibly generated by Blender Python
- Camp no longer relies on CSS hills / ground / Unicode prop stand-ins
- the same physical Fusion altar is used in Camp and Fusion close-up
- Training Dummy is used both for Camp training feedback and Fusion attack preview
- Nursery uses a physical 3D station
- weapon-related Camp presentation is excluded from this vertical slice
- 390×844 production QA passes
- authoritative game-state flow remains unchanged
- build is deployed without overwriting the parallel model/motion gallery work
